Let agents use the page they built: OpenCode 2's browser plugin, with Fleet as the browser

OpenCode 2 ships a browser plugin: an agent can open a tab, read the page, click, fill a form, read the console and take screenshots, all from one Code Mode script. OpenCode's desktop app normally provides the browser. This spike made Fleet provide it instead, with the headless Chrome Fleet already runs for screenshots, and checked what it would take to give the same thing to every harness. The mockups use Fleet's own tokens and follow your theme.

Viable, with conditions

Fleet can be the plugin's browser. A small C# attachment inside a scratch Fleet ran a real agent script end to end: it opened the canvas's page, filled a field, clicked Save, read the result and the console, and sent a screenshot back to the model. Seven steps, one tool call, under a second of browser time.

  • Two browsers. The agent drives Fleet's headless Chrome; you watch an iframe in your own browser. Your view doesn't change when the agent clicks, so Fleet needs an honest "Agent's view".
  • No permission asks. OpenCode 2 runs browser actions without asking, even when shell commands ask. Fleet runs every action, so Fleet has to set the limits.
  • Fleet already pays for it. Every Fleet OpenCode 2 session carries about 1,000 tokens of browser tools that can't work today. That's worth fixing whatever you decide.
Today

The agent can only look

fleet_browser_screenshot loads a page fresh and hands back a picture. The agent can't open a menu, submit a form, see a validation message or read a console error. "It works" means "it renders".

With this

The agent can use the page

It opens its own tab on the app in the browser canvas, reads the page as text with element refs, clicks and types, then checks the result, the console and failed requests. Many steps go in one Code Mode call.

You see it

Every step, live

Fleet runs each browser action itself, so it can list the steps in the conversation and show a live picture of the agent's tab in the canvas. Your own view of the page stays yours.

What Fleet gains

Checks the flow, not just the look

The fleet-run skill tells agents to check what they changed. With a page they can use, "check" includes signing up, saving, paging and the error path, not only a screenshot.

Console and network, from the page

fleet_canvas_read shows the server's output. Browser errors, a 404 on a script or a failed API call only show in the page. The agent reads them directly.

Seven steps, one round trip

In the live run, open → read → fill → click → read → screenshot → console was one execute call. As separate tools that is seven model round trips, each re-sending the context.

A cost Fleet pays for nothing today

OpenCode 2.0.18 puts 45 browser tools in every session's catalog (about 1,000 tokens in a Fleet session). Without a browser behind them they only fail. Either turn them off or make them work.

What each harness gets

Native first, then Fleet, then off with a reason. The browser work is Fleet's in every row: one agent-browser service in Fleet, reached two ways.

In the conversation
    
        
  • One execute call becomes a "Used the browser" card with one line per step, because Fleet ran each step and knows what it was. Fleet doesn't parse the script.
    • 
        
  • A screenshot step shows the picture, as fleet_browser_screenshot does today. The script stays one click away.
    • 
        
  • The same card draws OpenCode's one-step fleet_browser_act calls, so every harness looks alike.
    • 
      

      
In the canvas
    
        
  • Your view is the page in your browser, as today. While the agent has a tab on it, a banner says so.
    • 
        
  • Agent's view is a live picture of the agent's tab, from Chrome's screencast. The current element gets a ring and the step a caption. It is read-only.
    • 
        
  • The header chip counts the agent's open tabs. Fleet closes them when the turn has been idle a while.
    • 
      

      
Why not move your view?
    
        
  • Your iframe runs in your browser, which Fleet can't drive. Replaying the agent's clicks there would submit the form a second time.
    • 
        
  • Fleet's desktop app could later give the agent the very page you see, as OpenCode's own desktop does. Not in v1.
    •

Why these defaults
    
        
  • OpenCode 2 never asks before a browser action (checked live at Fleet's "Ask" level: the shell call asked, the browser calls didn't). So the limits live in Fleet, where every action passes.
    • 
        
  • "This session's pages" covers the job, trying the app the agent is building, and keeps the agent off your other local services.
    • 
      

      
No per-session switch
    
        
  • The setting applies to every session. A session that doesn't need the browser never opens a tab, so it costs nothing beyond the tool list.
    • 
        
  • Whether to add a per-session switch is an open question (Plan tab).

OpenCode 2 owns the tools, the agent's script and the tab list it trusts. Fleet owns the browser, the limits and what you see. They talk over V2's own event stream and plugin RPC; nothing new is installed.

OpenCode 2 specifics stop at its adapter
    
        
  • The attachment lives in Harnesses/OpenCode2. The browser service, its limits, the step event and Agent's view are shared, behind a HarnessCapabilities flag.
    • 
        
  • OpenCode gets the same service through two Fleet tools in its own plugin. No shared code between the two adapters.
    • 
      

      
Version churn
    
        
  • The plugin changed three times in the week after 2.0.18. The RPC id is experimental.browser, protocol version: 4.
    • 
        
  • Fleet answers unknown operations with "not supported" (the desktop does the same), and checks the version on attached.
    •

2.0.18 shows the browser tools to every session, and they fail

        
OpenCode 2 alone, scratch HOME. No attachment. The model's system prompt lists browser (45 tools, 7 shown); a call returns:


"tabs": { "error": "[browser.disconnected] No desktop browser is connected to this session. Open this session in the desktop app and wait for it to connect. …" }

      

      

        
2.0.21 hides them, but Fleet's "allow everything" rule brings them back

        
Same prompt, OpenCode 2.0.21. A session with no rules of its own: Unknown tool 'browser.tabs.list', no browser namespace. A session created the way Fleet creates them ({"action":"*","resource":"*","effect":"allow"}): browser (45 tools, 7 shown) again, same error. After an attachment, the session gets browser: allow and the catalog arrives as a <system-update> message (8,924 characters), so the system prompt and its cache stay as they were.

      

      

        
What it costs in tokens

        
Characters sent to the model, measured from the scripted model's request log (÷4 ≈ tokens).

        

      

      

        
No permission asks for browser actions

        
Scratch Fleet with the permission level set to "Ask". The seven browser steps ran with no ask: GET /api/sessions/{id}/permissions stayed []. In the same session, a shell call asked at once:


[{"kind": "shell", "tool": "shell", "title": "echo from-tool", "always": ["echo *"], …}]

      

      

        
Memory

        
Fleet's headless Chrome with one agent tab open: 11 processes, 242 MB (PSS). The OpenCode 2 server was 140 MB and Fleet 188 MB. The machine had 2.5 GB free with all three running.

      

      

        
What I couldn't check

        
Not run: evaluate, network, files, traces, heap and Lighthouse through Fleet; the screencast for Agent's view; a real model choosing between the two screenshot tools (the scripted model only does what it's told); whether V2's tool editor lets one plugin rewrite another's descriptions; how a remote Fleet machine would attach; Claude Code's and Pi's routes for Fleet tools.

Questions for you

    

      
1. Build it?Steps 2–5 are about two weeks and give OpenCode 2 the browser; step 6 adds OpenCode.My recommendation: yes, OpenCode 2 first.

      
2. On or off by default?It can click and submit forms in your local apps.My recommendation: on, limited to the session's own pages, with scripts off. Or off until you turn it on, if you'd rather opt in.

      
3. Agent's view in the first version?It's the part that lets you trust what the agent did; without it you only get the step list.My recommendation: yes, with the step list.

      
4. Ship step 1 now, on its own?It removes ~1,000 tokens from every OpenCode 2 session today, whatever you decide about the rest.My recommendation: yes.

      
5. A per-session switch as well as the setting?The mockup has none: a session that doesn't use the browser pays only for the tool list.My recommendation: not in v1.
