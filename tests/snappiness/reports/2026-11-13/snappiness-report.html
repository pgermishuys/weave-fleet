Fleet UI snappiness: v0.60.0 vs main

Measured 13 Nov 2026 on taron (Windows, 16 GB) against scratch Fleets seeded with invented data. v0.60.0 (21 Oct) is the last release before the layout, machines, folded-turns and Changes-review wave; main is 1e5a98f6.

Summary

At normal CPU speed most of the UI got faster, not slower: cold start, opening and switching sessions, rail switches and sending are 11 to 92% quicker on main.

One regression explains the "slower" feel, and it's big: with a diff open in the Changes panel, every repaint got expensive. On a slower CPU (4× throttle) a keystroke takes 161 ms to show instead of 38 ms (p95 445 vs 59 ms), and four streaming sessions cost 1.1 s of blocked main thread every 6 s instead of 0.06 s. Cause: the new Changes review panel gives every diff line two position: sticky number cells (1,569 for 11 files), and each repaint re-layerizes and re-hit-tests all of them. Fixed on branch perf/changes-sticky-gutters: typing back to 50 ms median, streaming long tasks −85%.

The rest of the slowdown is the same panel mounting: on a slower CPU, opening a session whose folder has changes costs 32% more (1.4 → 1.9 s at 4×), because the full review renders with it; opening the Changes tab is 7× slower (21 → 142 ms at 1×). Those belong to the Changes session's investigation, with the numbers below.

1 · Sticky line numbers in the Changes review panel slow every repaint (regression, fixed)

Symptom. Typing, sending and streaming are slower only in sessions whose folder has changes. At 4× CPU, keystroke → paint median 38 → 161 ms, p95 59 → 445 ms; long tasks while four sessions stream 57 → 1,097 ms per 6 s; a sent prompt settles in 2.1 s instead of 0.6 s. With no changes in the folder, main types as fast as v0.60.0 (median 40 vs 39 ms), so the composer itself isn't the cause.

Evidence. A Chrome trace of typing 28 characters (same session, same edits, 4×):

v0.60.0main
Layerize162 ms767 ms
HitTest8 ms248 ms
Commit23 ms201 ms
Layout~8 ms/key~12 ms/key
Long tasks018

Script and layout barely moved; compositing did. The Changes panel on main renders every diff line inline: 4,920 DOM nodes (v0.60.0's Changes list: 138), with 1,569 position: sticky elements, the line-number cells .rline__no (client/src/components/canvas/ChangesReview.vue:910–911, 934, 946, 995–996, 1027, 1046; sticky rule at :1512), inside 20 horizontal scrollers .rscroll (:1479). Introduced by #862 (9 Nov, "review panel"). What-if runs that only injected CSS confirmed it: .rline__no{position:static} took typing from 135/422 to 49/90 ms (median/p95); hiding the scrollers' fade mask did nothing; content-visibility per hunk recovered most of it.

Fix (branch perf/changes-sticky-gutters, 1 file + test): the numbers are static until their hunk is scrolled sideways; one passive capture-phase scroll listener on the review root toggles .rscroll--scrolled, and only there they stick. At scrollLeft 0 a static number sits exactly where a sticky one did, so nothing moves; scroll a long line and its numbers still stay put. 2 · The Changes review renders in full on open (left to the Changes session)

Opening a session whose folder has changes: 1,399 → 1,851 ms at 4× (+32%; settled +69%), busy CPU 1,961 → 2,799 ms. Profile diff, main vs v0.60.0: ChangesReview.vue mount +103 ms, use-file-diff-contents.ts +41 ms, diff-parser.ts +8 ms, and +371 ms of native DOM/layout work for the thousands of review nodes. Going back to Sessions (+32%) and cold start to a conversation (+30%) pay the same at 4×. Removing the sticky gutters doesn't change these (what-if: 1,248 vs 1,170 ms): it's the eager render itself. At 1× these are hidden by main's other gains.

Picking the Changes tab: 21 → 142 ms at 1×, 85 → 777 ms at 4×, with 122 ms of long tasks where v0.60.0 had none. The panel now renders the whole review (every hunk) on open rather than a file list. The Changes session ("Changes panel sluggish / won't load") owns the root cause; it also found that with Changes open on a 353-file session, Ctrl+F queued every other API call for ~71 s behind the browser's 6-connection limit. Its PR (branch fix/changes-sluggish) caps file fetches at 4 per machine and shares one /diffs on open. A suggestion for it: render a file's hunks when the file scrolls into view (or is expanded), so the panel's first paint is the file list, as in v0.60.0.

3 · Mounting a long conversation is the biggest cost left (not a regression)

Switching to a 60-turn session takes 400 ms at 1× and ~3 s at 4×; returning to Sessions from another view costs the same, because the conversation mounts again. v0.60.0 is no faster (582 ms / 3.2 s). In the 4× profile (2.7 s busy) the top app frames are each bubble's rendered computed, client/src/components/session/MessageBubble.vue:107 (markdown-it, ~425 ms inclusive), and highlight.js at ~270 ms self: every bubble re-parses its markdown and re-highlights its code on every mount, with no cache. After the first render, client/src/stores/file-links.ts resolves the paths the text names, and each bubble that names a file renders its markdown again (both versions).

Proposal (a design choice, not built): (a) a small module-level cache of rendered HTML keyed by message id and text, so revisiting a session or coming back to Sessions skips markdown and highlighting (cheap, likely the biggest win); (b) highlight code blocks when they scroll into view; (c) render file links as a DOM pass after the HTML is in, not by re-rendering markdown. client/src/components/session/DiffView.vue:211 also gives every line a sticky number, the same pattern as cause 1, in the file diff view (older than v0.60.0); the same fix applies.

Checked and ruled out

  • Whole-list re-renders on SignalR events: four sessions streaming 60 updates each while you read an idle session (no diff open) cost 0 ms of long tasks on both versions; watching a streaming conversation, 0 ms median. The session list doesn't re-render per event.
  • A tab that slows over the day (leaks): 120 session switches in one tab: heap 31 → 38 MB after GC, DOM nodes and listeners back to their baseline (1,477 listeners), switch time flat (long 323–443 ms, short 135–188 ms). Same shape on v0.60.0.
  • Unvirtualized long lists while scrolling: 3 s of wheel scrolling through a 60-turn conversation holds 60 fps at 1× on both; at 4× main drops fewer frames (71 vs 84) with fewer long tasks (1.0 vs 1.6 s).
  • Too many requests on navigation: opening a session makes ~22 API requests on both versions (a lot, but not new); the New session page 2 (3 at 4×).
  • New session page: +17% at 1× (90 → 106 ms) but −11% at 4×: within noise.
  • Bundle: JS decoded at cold start 2.58 → 2.79 MB (+8%), 232 → 238 requests; cold start is still 38% faster.

Method

Data. Each build gets its own scratch Fleet in test-harness mode (own profile folder, databases, port, 127.0.0.1), seeded through the API with the same invented data: 6 git projects, 150 sessions (3 of 60 turns with 4 to 10 tool calls each, 12 of 10 turns, the rest short), markdown answers with code blocks and tables, tool calls with output and diffs; four sessions primed to stream 60 updates each. The long session's folder gets 10 edited files and one new one (as the Changes scenario does). Not covered: a second machine, real harness traffic, the desktop shell.

Timing. Headless Chromium 134 via Playwright, 1440×900. Each interaction is timed from the real input's timeStamp (pointerdown/keydown) to the frame after the expected content is on screen ("shown"), and to 300 ms of DOM quiet ("settled"); keystrokes from keydown to the next frame; long tasks, long animation frames and Event Timing from PerformanceObservers; requests in the window. Clicks go to coordinates resolved beforehand, so the harness's own work never lands in a measurement.

Runs. 5 runs × 2 rounds per build, builds alternating each round (another session was benchmarking on the same machine), at 1× and at 4× Chrome CPU throttling (a slower laptop; it magnifies costs that are a few ms here). Median and p95 of 10 samples. A CPU profile per scenario (source-mapped to src/…:line) and Chrome traces for typing.

Rerun it

cd tests/snappiness
bun install; bun x playwright install chromium     # once
bun run.ts --refs v0.60.0,HEAD --throttle 1,4      # builds both, seeds, measures, writes compare.md (~70 min)
bun run.ts --refs HEAD --only typing,switchLong --runs 3   # a quick look at this checkout

The kit is on branch snappiness/check (tests/snappiness, README inside). It also has attribute.ts (profile → file:line), trace-typing.ts (where a keystroke's time goes), soak.ts (does a tab age) and --css what-if runs.

Keeping it from regressing

Proposal: a snappiness budget job on PRs that touch client/. Build the SPA and API (already done for E2E), seed one scratch Fleet (~2 min), run five scenarios at 4× (typing with a diff open, switchLong, openSession, sendPrompt, streamingList), 5 runs each (~4 min). About 10 CI minutes per PR. Budgets: fixed thresholds with generous headroom (runner CPUs vary ±30%), e.g. keystroke → paint p95 ≤ 120 ms, 0 long tasks while typing, switchLong median ≤ 4 s, streaming long tasks ≤ 400 ms per 6 s; plus counts that don't vary with CPU (API requests on session open ≤ 25, sticky elements in the Changes panel ≤ 200).

And nightly: the full A/B against the last release at 1× and 4× (~70 min, off the PR path), posting compare.md as an artifact, so slow drifts show up within a day.
