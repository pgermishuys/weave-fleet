One Fleet interface, many machines doing the work

Run a headless Fleet node on each machine with the CLI, and work with all of them from one interface. Pick which node a session, automation or workflow runs on, or let an agent hand work to another node. This page shows where we are, the two ways to wire it, what the screens would look like, and a plan you can shape at the end.

Proposal only. Nothing here is built. Machine names, projects and sessions are made up.

1 · Today

Every machine runs everything, and the UI works with one at a time

Most of the building blocks shipped in the multi-machine work (#318–#320, #331, #397). What's missing is a node without a UI, and a UI that's live on every machine at once.

live connection: events, terminals, diffs list refreshed by polling

  • Built The sidebar shows every machine's sessions as the same tree.
  • Built The composer can start a session on another machine.
  • Built The machine serving the page already holds a live connection to every other machine, but only to forward phone notifications.

2 · Two kinds of customer

One Fleet. The simple case stays simple; nodes are something you add.

Nobody is left out. The desktop app keeps working exactly as it does today. Advanced customers add nodes to the same app, or point a browser at a Fleet that knows them. No separate edition, and no feature only one group gets.

Simple · most customers

Install the desktop app, and it just works

One computer. The app starts its own Fleet and shows it. They never see the word "node", and nothing in this proposal changes their first run or their defaults.

Advanced

Run fleet node on other machines, and point a UI at them

A server, a cloud VM, a Mac mini under the desk. The UI is the same desktop app with the nodes added, a browser on a Fleet that knows them, or the phone through its paired machine.

Rules so nobody is left out

  • Defaults don't change. The desktop app's first run, fleet with no arguments, and the browser on localhost behave as today.
  • No node words in the simple path. They appear once you add a second machine.
  • macOS, Windows and Linux get each piece before it's announced, install-service included.
  • Older and newer Fleets work together, so customers update one machine at a time, when they choose.
  • Hosted Fleets with sign-in aren't touched.

Ways to point a UI at a node

  • Desktop app: Settings → Machines → Add a machine. Its own Fleet is the interface and keeps the list.
  • Browser: any full Fleet (fleet) that has the node in its list, such as an always-on box.
  • Phone: through its paired machine, as today.
  • A headless node has no page of its own. That's what keeps it small; any of the above is its UI.
3 · Two ways to split it

A node is a whole Fleet without the UI. The question is who connects to whom.

Both options keep each session, its worktree, git, terminals and keys on the node that runs it. The interface keeps only the list of nodes and your sign-in. They differ in which way the connection goes.

A

The interface connects to each node

Start here

Good

  • Builds on what's merged: tokens, CORS, the machine list.
  • No middleman. Each node is reached directly, so terminals stay fast.
  • If one machine is down, the others still work.

Costs

  • Every node must be reachable from every device, phone included. In practice: Tailscale.
  • A token per node to copy and paste.
  • Previews on another node still need work (cookie-bound).
B

Each node connects out to a control plane

Bigger

Good

  • Nodes work from anywhere: behind NAT, in the cloud, no Tailscale.
  • Join with a one-time code. No tokens to copy around.
  • Phones only need to reach one machine.

Costs

  • The control plane relays everything, terminals and previews included.
  • Control plane down = no access (nodes keep running).
  • A new tunnel to build, secure and keep alive.

Why the node can't be any thinner

A thinner node is possible on paper: one central Fleet keeps every session, and nodes only run the harness process. It doesn't fit how Fleet works:

  • Harnesses call back into Fleet over loopback for Fleet tools, memory and asks.
  • Worktrees, git, diffs, file views, terminals and previews all read that machine's disk.
  • The harness boundary (IHarnessSession, about 30 methods plus an event stream) would need a remote twin for each of those.

So a node is the same Fleet binary started with fleet node: no web UI, token required.

What's new here

  • Any node lets Fleet choose. It always says why, so the choice never looks random.
  • A node without the folder offers to clone it (the new-folder flow, #323, on that node).

How Fleet would pick

Simple rules, in order: the node is answering, has the folder, has the harness, then fewest sessions working. No load balancing beyond that.

What's new here

  • An automation names the node it runs on, or "any node".
  • If the node isn't answering, you choose: skip it, or move the run to another node. "Moved" runs say so.
  • Each workflow run happens on one node. Steps don't hop between machines: the code would have to travel through git between steps.

Where it runs from

The schedule has to live somewhere that's always on. In A, the node runs its own automations, so a laptop can be closed. In B, the control plane keeps the schedule and sends the run to a node.
