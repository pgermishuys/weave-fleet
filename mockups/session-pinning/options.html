Short answer

Do both, but keep reordering inside Pinned.

Pin the few sessions you keep going back to. They sit above your projects, and you drag them into whatever order you like. Everything else stays newest first in its project, the same as today.

That's option A. B, C and D are the other ways to do it, so you can compare them side by side.

Why not reorder the whole list

  • New sessions arrive all day. In a hand-ordered list, each one lands on top of your order, or at the bottom where you won't see it. Either way the order you made keeps getting disturbed, and you end up tidying it. Try "New session arrives" on D.
  • Pins are a short list that nothing joins on its own, so an order you set there stays put. That's where a custom order pays off.
  • It keeps the rule from September: rows only move when you move them. Pinning is something you do on purpose. Newest first keeps the rest predictable.
  • Projects can already be put in order (right-click › Move up / Move down), so the big picture is already yours to arrange.

Today

for reference

Sessions are grouped by project, newest first, and you can't change that order (SessionRepository sorts by created_at DESC). Projects can be moved up and down. Dragging a session onto another project's header moves it to that project. Quiet sessions fade after 1 and 3 days.

The session you go back to most, like a release checklist or a long-running investigation, sinks a little further every time you start something new.

A · Pinned group on top, drag to order it

recommended

Pinning a session moves it out of its project into a Pinned group above all projects. Inside Pinned, you set the order by dragging. Unpin it and it goes back to its project, in its usual newest-first spot.

Good

  • The sessions you care about are always in the same place at the top, no matter how many new ones arrive.
  • You only arrange the short list, and that order never changes unless you change it.
  • It uses the same header look as projects. The Pinned group folds the same way projects do.
  • Ways to pin: the pin button on hover, right-click › Pin to top, or drag a row into Pinned. To unpin, drag it back to its project.

Costs

  • A pinned session isn't shown under its project. The project count drops by one.
  • Needs a small server change so pins follow you to the phone app and other browsers.

B · Pins rise within their own project

alternative

Pinned sessions stay in their project but go to the top of it, with a small pin mark. You can drag pins into order, but only inside their project.

Good

  • Project grouping stays exactly as it is, and a pin never leaves its project.
  • Works well if you think in projects first.

Costs

  • Your pins are spread across projects. If a project is folded or far down the list, its pins are hidden with it.
  • No single place to get to your most important sessions.

C · Pinned shortcuts; sessions stay where they are

alternative

Pinning adds a shortcut to a strip at the top, and the session itself stays in its project with a pin mark. Hover a shortcut to see where the session lives. You can drag the shortcuts into order.

Good

  • Nothing in the project list moves, ever. This is the strictest version of "rows stay put".
  • You get one place at the top for quick access, like A.

Costs

  • Every pinned session appears twice. With a few pins the list gets longer and looks repetitive.
  • It's less obvious which row you're "in". Both rows light up when the session is open.

D · A, plus drag anything anywhere in its project

shown for contrast

Pinned works like A. On top of that, you can drag any session within its project. Once you do, that project switches from Newest first to Your order, and the header shows ↺ to switch back.

Good

  • Full control: every list is in the order you set.

Costs

  • New sessions have to go somewhere. They land on top of your order, so you have to tidy up after every new session. Press New session arrives a few times after dragging.
  • Sessions come and go much faster than projects or pins. Keeping a long list in order becomes a chore.
  • Two kinds of order (per project, and Pinned) to understand and to store.

If we build A

What it takes

Server

  • Add a pin_order column on sessions (a number; empty means not pinned). This is migration 056. Using fractional numbers means a drag only rewrites the row that moved.
  • PUT /api/sessions/{id}/pin with the session it now sits after, and DELETE to unpin. Both send the usual session-list update, so other tabs, the phone app and the desktop app all update.
  • Pins are saved on the server, not in the browser, so they're the same on your phone. Each machine keeps the pins for its own sessions.
  • Archiving a session unpins it.

Client

  • SessionsPanel builds a Pinned group above the projects, in the same style as ProjectGroup. With several machines, there's one Pinned group under each machine.
  • Row dragging already exists (it moves sessions between projects). Add the drop line between pinned rows, and let project rows be dropped into Pinned.
  • Hovering a row shows a pin button next to Archive. The right-click menu gets Pin to top / Unpin under Rename. Alt+↑/↓ moves a pin, and Ctrl+[/] follows the order on screen.
  • Filter matches pinned rows too. Quiet pins fade like every other row.

Questions for you

  1. Several machines: one Pinned group under each machine (simple, my pick), or one Pinned group across all machines at the very top?
  2. Archive: unpin when you archive (my pick), or keep the pin so Restore brings it back pinned?
  3. Fading: should quiet pinned sessions fade like the rest (my pick, because the fade still tells you that you haven't touched it), or always stay at full brightness?
  4. Sessions another session started: if you pin one, it shows on its own in Pinned, not under its parent. Is that OK?
  5. Which option? A as recommended, or would you rather have B, C or D?
