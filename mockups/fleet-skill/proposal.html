Fleet knows what it can do

An agent running in Fleet should know that Fleet can run work in parallel sessions, run it on a schedule, turn a process into a workflow, and remember things. It should offer those when they fit the request, without loading a manual into every conversation.

Demo sentence In any harness, ask “fix these three issues” and the agent offers three Fleet sessions, each in its own worktree. Ask “every weekday morning…” and it offers an automation. Sessions that never need Fleet pay about 80 tokens for this.

# What Fleet can do for the user

Fleet started this session. Its API is at $FLEET_URL; requests from this
machine need no token. If it's empty, Fleet didn't start you: don't suggest these.

| When the user wants…                      | Suggest                  | Read            |
|-------------------------------------------|--------------------------|-----------------|
| several independent tasks done            | a Fleet session per task | sessions.md     |
| something done on a schedule, once later, | an automation            | automations.md  |
|   or when something happens in Fleet      |                          |                 |
| a process they repeat, in steps           | a workflow               | workflows.md    |
| you to remember something                 | Fleet memory             | memory.md       |
| to change how Fleet behaves or looks      | the setting, or a mod    | settings.md     |
| to see something                          | a page or diagram canvas | (your fleet_* tools) |

## Suggest, then ask

Say what you'd create and why it fits, then ask. Sessions start agents,
automations keep running after this conversation, workflows are files in the
repo. Do it straight away only when the user asked for exactly that.

## Check what's on before you offer it

Memory, mods and some features are switches. Read them from the API
(settings.md) before you say something works; if it's off, say where the
user turns it on. Never switch a setting yourself.

## Look it up, don't guess

Request bodies are in $FLEET_URL/openapi/v1.json. Use the ids Fleet
returns, not your harness's session ids.

    # Automations

An automation sends a prompt on a schedule, once, or when something happens
in Fleet. It can start a new session, wake a tagged one, or run a workflow,
on this machine or another one in GET /api/machines.

## When to suggest one
"every weekday", "each morning", "on Friday at 4", "when a session finishes",
"remind me tomorrow". Prefer it to cron or a CI job when the work needs an
agent's judgement, not just a command.

## Show the user before creating
Name, when (in their time zone), folder, where it runs, the prompt, next run.

POST /api/automations
  triggerType: schedule (cron) | once (local date-time) | event (JSON string)

    workflows.mdnew
    # Workflows

A workflow is a list of agent steps in .weave/workflows/<name>.yaml. The user
runs it from Workflows with a request; each step is its own agent turn and can
stop for the user. Fleet ships some built in.

## When to suggest one
A process the user repeats with steps that need judgement: releases,
triage, a review routine. A plain script is better when every step is a command.

## Before writing one
GET /api/workflows?repository=… for what's there (don't duplicate a built-in).
Read one existing file for the format; the schema is in the OpenAPI document.
Write the file, then tell the user where to find it and how to run it.

    # Fleet memory

Fleet keeps notes for a repository or a machine and gives them to every new
session, on every harness. It's off by default.

GET /api/memory → { enabled, … }

- On: you have fleet_memory_save and fleet_memory_forget. Use them.
- Off: you don't have them. Say memory is off and that the user turns it on
  under Settings → Memory. Offer AGENTS.md as the other place.
Don't turn it on yourself.
    settings.mdnew
    # Fleet's settings

Where things are, so you can point the user to them:
- Features: the Mods switch and other switches
- Memory: memory on or off, and the notes
- Skills: built-in skills (fleet-code-review, fleet-design, …)
- Mods: the user's mods (shown once Mods is on)
- Permissions: what agents may do without asking
- Harnesses: OpenCode, Claude Code, Pi; install and update
- Machines: other machines Fleet can run sessions on
- Workflows, Weave, Browser, Tools, Folders, Appearance

Reading what's on: GET /api/memory, GET /api/preferences/{Key} (e.g. Mods).
You can read settings. Only the user changes them.

    How Claude Code gets it

    Fleet already gives Claude Code a skills folder: it starts claude with --add-dir pointing at a folder of its own, and Claude Code loads that folder's .claude/skills next to the user's. It's how this proposal's own session got fleet-mockups. The catch is that Fleet only writes the folder when the user has a built-in skill switched on, and only copies built-in skills into it.

    Today

    claude … --mcp-config <Fleet's tools> --add-dir ~/.weave/claude-code/skills/<owner> ← only if a built-in skill is on ~/.weave/claude-code/skills/<owner>/.claude/skills/ fleet-code-review/ fleet-design/ fleet-mockups/ … ← no fleet-api

    Folder written by ClaudeCodeFleetSkills.Sync; it keeps only names in BuiltInSkillFiles.Names and deletes the folder when that list is empty.

    With this

    claude … --mcp-config <Fleet's tools> --add-dir ~/.weave/claude-code/skills/<owner> ← always ~/.weave/claude-code/skills/<owner>/.claude/skills/ fleet/ SKILL.md sessions.md automations.md … ← always fleet-code-review/ fleet-design/ … ← as switched on

    The same folder, with Fleet's own skills from opencode/skills/ always copied in. About 40 lines of code and tests. Claude Code shows the skill's folder when it opens it, so sessions.md and the rest are read straight from there.

    New sessions only

    Claude Code lists skills when it starts, so sessions already running get the skill on their next start. Same as built-in skills today.

    Not through Fleet's MCP server

    Fleet's tools already reach Claude Code over --mcp-config, and an MCP server can send “instructions”. But those go into every request, which is the system-prompt cost again. The skill folder loads on demand.

    05How the agent behaves

    Suggest, then ask

    It offers the Fleet way with a reason and a preview. It creates sessions, automations or workflows only after a yes, or when the user asked for exactly that.

    Checks what's on

    It reads memory, mods and other switches from the API before offering them. When something is off, it says where to turn it on. It never changes a setting.

    Only when it fits

    No Fleet pitch for a one-line fix. Parallel sessions only for work that doesn't overlap; a workflow only when steps need judgement.

    Facts from the running Fleet

    Request shapes come from OpenAPI and on/off from the API, so the text can't go stale about this user's Fleet.

    06How we'll know it works

    The risk isn't the token count. It's whether the agent opens the skill at the right moment. So the wording gets an evaluation before it ships, the way fleet-design did: real prompts, run on each harness, on a scratch Fleet.
