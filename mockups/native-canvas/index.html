Pages on the phone

How the pages agents show (mockups, reports, choices, walkthroughs, explainers) could look and behave in Fleet's Android app. Every frame is drawn from how pages really work in Fleet today, read from the code. A few things need a small server change; those are marked. This is a proposal: nothing is built. All data is invented.

00How a page really gets to a screen

The design below rests on these facts. They decide what the phone can do cheaply and what it can't.

A page is a URL on the machine

fleet_page_show copies the page's folder into Fleet and serves it at {machine}/pages/{pageId}/, the same address and port as the API. It survives restarts and is deleted with its session.

PageEndpoints.cs · PageStore.cs
The phone needs no extra sign-in for it

Page routes are open by design: the random 128-bit page id is the key, as with previews. A WebView loads the URL as it is, with no device key, cookie or token. The flip side: anyone with the link who can reach the machine can open the page.

PageEndpoints.cs:11-33 AllowAnonymous
It stays sandboxed in a WebView too

Fleet sends the sandbox as a CSP header, not only as an iframe attribute. So a page opened in a WebView still has an opaque origin, can't read Fleet's cookies, and can't call Fleet as you. Scripts, forms and CDNs work.

PageEndpoints.cs:56 Content-Security-Policy
The theme goes in through window.name

Fleet puts a small script at the top of every page. It reads window.name = "fleet:{appearance, variables}" and listens for fleet:theme messages. The app sets the name before the page loads, from its own tokens (bg = panel, surface = card, accent, and so on). No DOM is needed to work them out.

PageTheme.cs · page-theme.ts FROM_APP
Pages talk to their host by postMessage

A page posts fleet:page-choice, fleet:page-reply, fleet:page-state and fleet:page-hello to parent. In a full-screen WebView, parent is the page itself. The app adds a short shim that forwards those to React Native, and replies the way the desktop canvas does.

page-bridge.ts · walkthrough.html:290
The host sends a choice, never the page

When the agent waits on a pick, the session reads Needs you (waiting_input). The page only proposes a pick. The host's bar sends it: POST /api/sessions/{id}/page-choices/{callId}/send, which the phone can call with its device key.

PageChoices.cs:84 · CanvasEndpoints.cs:84
The app hears about pages on the socket it already has

Tab pages arrive as canvas.updated (kind page) on the session's topic, and GET /api/sessions/{id}/canvases lists them. Conversation pages arrive as a tool call whose metadata has page: {id, entry}. The session list carries nothing about pages yet.

CanvasEndpoints.cs:22 · canvases.ts:461
One native module, one new build

The app has no WebView yet. react-native-webview is native code, so it ships in a new EAS build installed once. An over-the-air update can't add it. After that, page changes go out over the air as usual.

02Full screen, edge to edge, in Fleet's theme

The page fills the screen below one thin Fleet bar. The page draws its own ground from --fleet-bg, so it reads as part of the app in both themes. These two frames ignore the toggle above: the first is dark, the second light.

Dark
  • app The bar is Fleet's: back, the page's title, "4 of 4" and the session it came from, and ⋯ for Open in browser and Reload.
  • Below it the WebView runs to the screen's edges. No panel inset: a page needs every pixel on a phone.
  • The reply bar stays at the bottom; scrolling the page down hides the Fleet bar, scrolling up brings it back.
Light
  • works today The same page, same URL: only the variables in window.name differ. Fleet's theme script applies them before the page paints.
  • Switch the phone to dark while it's open: the app posts fleet:theme and the page follows without reloading.
  • A page that sets its own colours keeps them; the desktop canvas behaves the same.

06Choices to make

How the app loads a page. The facts in 00 make one of these much cheaper than the others.

AWebView on the page's URL Chosen

app→WebView→hangar/pages/{id}/

The app loads the same URL the desktop's iframe does, sets window.name to the theme first, and adds a shim that hands the page's messages to the app.

Build
react-native-webview, a page screen, a shim of about 40 lines, the choice bar and the reply sheet.
Ships
One new EAS build, installed once; then over the air.
Safety
Same sandbox as the desktop, from Fleet's CSP header.
Offline
Nothing to read when the machine is away.
Server
None, apart from the page count on the list.

BThe app downloads the page, the WebView shows its copy

app→fetch files→phone storage→WebView

The app fetches the entry and every file listed in the page's state, saves them on the phone and opens the copy.

Build
Everything in A, plus a downloader, a cache with a size limit, and clearing pages when sessions go.
Ships
The same one new build.
Safety
Weaker. A CSP sandbox can't be set from a file or a meta tag, so pages saved on the phone could read each other.
Offline
Pages you opened before can be read anywhere.
Server
None.

COpen every page in the phone's browser

app→Chrome Custom Tab→hangar/pages/{id}/

The app just opens the URL in a Chrome tab over the app.

Build
A link. No new build if expo-web-browser is in it; it isn't yet.
Ships
Fastest.
Safety
Same sandbox.
Gaps
No theme (it falls back to Fleet's dark defaults), and no choices, no Ask about this, no remembered state. It leaves the app.
Server
None.

Which way should it page?

Three ways to…Waiting
3 · Only as cards in the conversation

1In the session sheet Chosen

Pages join Changes and Files, as on the desktop's right panel. Nothing new to learn, one more segment to build. A page is two taps away, or one from the strip's Pages count.

2A Pages tab in the session

One tap, and thumbnails help you find the right page. It takes header room in every session, even the many with no pages, and thumbnails need Fleet to save a picture when it checks each page.

3Only as cards

Nothing to build beyond the card. In a long session, the page you want has scrolled far up, and re-shown pages appear several times.

07Decided, 24 October 2026

  1. Loading: A. A WebView on the page's own URL, with the theme in window.name and a shim for the page's messages.
  2. Where pages live: 1. A Pages segment in the session sheet, next to Changes and Files, plus cards in the conversation.
  3. Sharing: Open in browser only. No Share or Copy link on the phone.
  4. Offline: say so. Follows from A. No copy is kept; the app says the page is on hangar and opens it when hangar is back.
  5. Notifications: the session row only. A page that asks nothing shows "2 new pages" on its row (needs the server's page count). A waiting pick still notifies as an ask.
  6. Inline pages: a card. Pages shown inline on the desktop are cards on the phone that open full screen.
