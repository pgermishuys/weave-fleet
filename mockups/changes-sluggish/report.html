  • A: a magnifier in the Changes header opens the find bar (Ctrl+F inside Changes still works).
  • C: GET /diffs/search?q= runs one git grep of the working tree and one of the base over the changed files, and find then loads only the files that match. A machine on an older Fleet, which can't answer, gets the old search over every file, so your machines don't all need updating at once.
  • Live updates: the first edit opens a 250 ms window and the refresh runs at its end; edits inside the window don't push it back, and only one refresh runs at a time. Keeping up costs git work: 142 git processes over that 8 s run, against 13 when Changes waited for the agent to stop.
  • Drawing: an open file is fetched and drawn once it comes within 600 px of view, and stays drawn. While it loads it holds about its height, so the files below don't all slide into view and load at once.

On your setup: the desktop app is Electron 44, so it is Chromium loading Fleet over plain HTTP, with the same 6-connections-per-server limit and the same per-file CORS preflight to other machines that I measured in Edge. One search request instead of hundreds of file requests matters most there.

What I found

  1. Every file's diff re-listed the whole repository. GitDiffService.cs:252–264 (ComputeFileDiffWithContentAsync) answered /diffs/file by running the full change listing again: diff --numstat (:317), diff --name-status (:322) and ls-files --others (:330) over the whole repository, plus 3 git calls to resolve the base, just to find one file. That cost nothing while Changes was a list you clicked one file at a time. The review panel (#862, 9 Nov) opens 8 files at once (ChangesReview.vue:125, 168), and find (#918, 12 Nov) loads every file (ChangesReview.vue:442). In the big repository, opening Changes cost 31.3 s of git and the first diff took 9.3 s.
  2. “Won't load” #1: find freezes the whole app. Ctrl+F in Changes on the 353-file diff sent all 345 file requests at once (use-file-diff-contents.ts:56). The browser keeps only 6 connections per server, so every other request (opening a session, sending a message) queued behind them. An unrelated request took 71 s. Fleet ran 2,375 git processes (235.6 s of git).
  3. “Won't load” #2: a failure is shown as “No changes”, or as nothing at all. When /diffs fails, ChangesCanvas.vue:83 ignores the error and says “No changes in this session yet.” The empty-panel rule (SessionsV2RightPanel.vue:155–159) then reads the failure as an empty session and keeps the panel shut. A file whose diff failed says “Couldn't load this diff.” (ChangesReview.vue:856) with no way to try again, and stays that way until the agent edits the file.
  4. Each session opened ran /diffs twice. The right panel (SessionsV2RightPanel.vue:59, 81) and the session page (routes/sessions.$id.tsx:145, 185) each fetched it. That's a second full git listing per open and per switch.

Ruled out by measurement: a held .git/index.lock (no slowdown, no errors); live edits causing a refetch storm (20 saves in 8 s caused 1 list and 1 file refetch). The opposite is true: the 500 ms debounce (use-diffs.ts:141–147) keeps restarting while saves arrive faster than that, so Changes doesn't update until the agent pauses.

The fix (PR, details below)

  • /diffs/file asks git about that one path only (a literal pathspec) and refuses a path outside the session's folder before running git.
  • At most 4 file diffs in flight per machine, so Changes can never take all 6 browser connections. The other app request during find dropped from 71 s to 15 ms.
  • The page and the panel share one /diffs request when a session opens.
  • A failed /diffs opens the panel on “Couldn't load the changes” with Try again. A failed file diff has Try again.

Still slow after the fix

  • Find still loads every file to search it. With the fix the app stays responsive, but searching all 345 files of the large diff still takes 53 s (80.9 s of git: about 7 git processes per file, 3 of them only to resolve the base again).
  • Another machine pays a CORS preflight per file. All 7 of 7 /diffs requests to the other machine needed one, because the browser caches preflights per URL and each file has its own ?path=. That's an extra network round trip per file over a real network.
  • The review panel draws every diff line up front (measured by the UI-snappiness session at 4× CPU slowdown, 10 edited files + 1 new): opening a session whose folder has changes went from 1,399 to 1,851 ms (+32%), with about 4,900 review elements against 138 for the old list, mostly browser layout (+371 ms) plus mounting the panel (+103 ms). Typing in the composer was about 4× slower while a diff was open; that session is fixing the typing part (sticky line numbers) on perf/changes-sticky-gutters. The open-session cost remains.
  • Outside Changes: a fresh page took about 15.6 s to list the other machine's sessions (on the build before #932, which changed exactly that this morning). Not re-measured.

Find in Changes: proposal

Find already exists on main (#918, merged 12 Nov), but you can only reach it with Ctrl+F while focus is inside Changes. There's no button, and Ctrl+F anywhere else opens the browser's or the conversation's find. That alone may explain “there's no find”. Three options, drawn with the find bar's own CSS:
