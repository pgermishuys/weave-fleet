A terminal under the chat

Each session gets a real shell in its own folder, in a drawer below the composer, the way t3code does it. The drawer spans the conversation column only, so Changes stays open beside it. The agent never reads it. You select lines and add them to your message. Try it: click the terminal and type, drag the top edge, select a few lines, or press Ctrl J.

What's on the mockup

Hover a note to find it on the mockup. Tags say whether it's in the first version.

  1. A

    A drawer under the chat

    First version

    It sits below the composer and spans the conversation column only, so a diff and its test run are visible together. Drag the top edge to resize; double-click resets it.

    272px default · 140px to 60% of the sheet · height kept per window
  2. B

    Tabs named by what's running

    Later

    A tab shows npm rather than zsh while a command runs, with a green dot. Closing it asks first if something is still running. Each tab is its own shell in the session's folder.

    server checks the shell's child process · every 1s, backing off to 60s
  3. C

    Select lines, add them to your message

    First version

    The agent can't see the terminal. Select output and it goes into the composer as a chip with the terminal and line range, so you choose what it reads and what it costs.

    chip “zsh · lines 9–11” → sent as a fenced block in your message
  4. D

    Hiding it doesn't stop it

    First version

    The shell runs on the server. Hide the drawer and the dev server keeps going; the header button gets a green dot while anything runs. Closing a tab ends that shell; archiving the session ends them all.

    Ctrl J / ⌘ J toggles · shells live until tab close, archive or idle timeout
  5. E

    The shell gets the keyboard

    First version

    While the terminal has focus, Esc, Ctrl K, Ctrl B and Ctrl [ go to the shell, not Fleet. The status bar says so. Try pressing Esc in the terminal.

    Fleet keeps Ctrl J, Ctrl Shift B and the platform copy/paste keys
  6. F

    Output survives a reload

    First version

    Scrollback is saved on the server, so a page reload or a Fleet restart brings it back. Terminal queries are stripped before replay, or the shell prints the answers as junk at the prompt.

    ~/.weave/terminals/{session}/{terminal}.log · 5,000 lines

First version

  • A shell per terminal tab on the server, in the session's folder: macOS, Linux and Windows
  • A terminal socket of its own, separate from session events and the database
  • xterm.js themed from Fleet's tokens, in the drawer shown here
  • Saved scrollback, Fleet's own variables kept out of the shell, and the socket's Origin checked
  • Select lines and add them to your message
  • Turned off when Fleet is hosted for several people

Later

  • Tabs named after the running command, and a prompt before closing one
  • Split terminals side by side
  • Dev-server addresses opening in a browser canvas
  • Terminals the agent starts itself, for dev servers and watch mode
One decision for you

Terminals belong to a session here: switching sessions switches the drawer, and each shell starts in that session's worktree. The alternative is one set of terminals per project, shared by its sessions. Per session matches t3code and keeps worktrees apart.

The shell and tokens match Fleet 0.18.0 (client/src/assets/main.css on main). The drawer follows t3code's ThreadTerminalDrawer.tsx and apps/server/src/terminal/Manager.ts. The session, files and terminal output are examples, and the shell only knows a few commands: ls, git status, pwd, clear, npx vitest run sessions, npm run dev:mock.
